Legacy Orders modernization summary

I wrote a modernization plan with the agent prompts, the target architecture, and validation gates for each phase. I also linked it from README.md. I haven't run either agent or deployed anything yet.

Neither agent will turn this WinForms app into a web app plus Windows container service on its own. They cover the .NET upgrade and the Azure dependency work; the API, the web frontend and the ACI deployment need custom prompts and engineering review.

1. Upgrade to .NET 10 — GitHub Copilot upgrade

This is a good fit: the upgrade agent supports Windows Forms and .NET Framework → .NET 8 or later.

  • Use it to convert the projects to the modern SDK-style format and target net10.0-windows, keeping current behavior.
  • Rebuild the COM pricing component as an x64 .NET 10 COM server, because the container backend must be x64.
  • Keep the upgraded WinForms app as a working reference while the business logic is pulled out of the form code into shared libraries.

The upgrade produces a .NET 10 WinForms app, not a web app — the agent has no WinForms-to-web scenario.

2. Windows container on Azure Container Instances (ACI)

GitHub Copilot modernization handles the Azure-specific changes:

  • Blob Storage for attachments, invoices and exports
  • OpenTelemetry for logging
  • Microsoft Entra ID for sign-in and roles
  • Managed identity for Azure SQL and Storage access

Moving orders.json to Azure SQL needs a custom prompt, because a JSON file isn't one of the database sources the agent recognizes.

ACI is feasible here, but with an important constraint:

  • ACI documents only Windows Server 2019-family base images.
  • Microsoft publishes official .NET 10 Windows images only for Windows Server 2022 and 2025.
  • Workaround: a self-contained .NET 10 x64 build on windowsservercore:ltsc2019.

ACI's Windows limits also shape the design:

  • No volume mounts or extra containers: the backend must keep no local state.
  • No public endpoint with VNet: the container sits on a private network with a NAT Gateway for outbound traffic.
  • Private IP can change: it may change when the container is recreated, so each deployment must update the API gateway's backend address.

Treat this as an experiment platform. For long-term production, consider AKS with Windows node pools on Windows Server 2022/2025.

3. Frontend architecture

Recommendation: a Blazor WebAssembly UI hosted on Azure Static Web Apps Standard.

Browser / Static Web Apps
        |
   Entra token + HTTPS
        v
API Management Standard v2
  CORS, token validation, rate limits
        |
 private network connection
        v
Private Windows ACI backend
        |
Azure SQL + Blob Storage

Static Web Apps can't link directly to ACI, and its linked backends can't be on a private network. So the browser calls API Management directly, and API Management forwards to the private ACI backend.

Desktop features get web equivalents:

Desktop featureWeb equivalent
File dialogs, Explorer menuBrowser upload
Opening files with Windows appsAuthorized downloads
Word/Excel automationServer-generated DOCX/XLSX
Local file lockServer-side handling of concurrent edits

Open questions to check early:

  • COM in the container: confirm the .NET 10 COM server registers in a Windows Server 2019 container and handles concurrent requests.
  • Managed identity with VNet: the ACI docs are ambiguous about region support, so test it in your target region.

Before running the agents

This project is currently untracked inside the Git repository rooted at your user profile. The upgrade agent creates branches and commits, so move the project into its own repository first.

The .NET 10 SDK and Docker aren't installed on this machine. Either use a Windows host with Docker in Windows-container mode, or build the image in Azure Container Registry with --platform windows.
